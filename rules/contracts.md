# 契约管理

- 跨服务及前后端通信先明确契约，再实现调用方与提供方；契约文件与实现代码一起版本管理。每种接口确定唯一的契约事实来源，避免文档、生成代码和手写类型各自演进。
- HTTP API 使用 OpenAPI 描述路径、方法、参数、请求/响应 schema、状态码、鉴权和错误结构；修改接口时同步更新 OpenAPI。可从契约生成客户端/类型或从代码生成规范，但在项目内固定一种方式，并在 CI 检查生成结果与实现一致。
- gRPC 使用版本化 `.proto` 文件定义 service、message、字段编号与 RPC 语义。生成代码由构建工具产出，不手工修改；删除字段时保留 `reserved` 编号及名称，不复用旧字段编号，不随意改变字段含义。
- RabbitMQ 消息也要有可追踪的契约：定义事件名称、版本、字段、发布方与消费方、幂等标识及兼容策略；复杂或跨团队消息采用明确的 schema 格式，而非只依赖示例 JSON。
- OpenAPI 校验：默认用 Spectral 检查规范和团队规则，用 openapi-diff 将变更后的契约与目标分支/已发布版本比较，识别破坏性变更；再通过提供方测试或生成结果检查确认实现与契约一致。lint 和 diff 不代替实际接口测试。
- Proto 校验：默认用 Buf 执行 `buf lint` 和 `buf breaking`，以目标分支/已发布版本的契约为兼容性基线；还应通过编译生成代码和提供方/消费方测试验证 RPC 行为。字段编号、`reserved` 等兼容规则纳入检查。
- 消息契约校验：JSON 消息采用版本化 JSON Schema，使用 ajv-cli 校验 schema 和代表性 payload（有效与无效样例）；消息路由、发布方/消费方需要文档化时用 AsyncAPI 描述，并用 AsyncAPI CLI 校验文档，payload schema 从同一契约源引用，避免重复定义。Protobuf 消息使用 Buf 校验 `.proto`。所有消息格式还需消费方测试验证实际序列化、解析与兼容行为。
- 将契约校验工具版本、规则集、兼容性基线和执行命令固定在项目配置与 CI 中；引入具体工具或选择消息格式时，按 [`general.md`](general.md) 与我确认，不为了通过检查而关闭兼容性规则。
- 契约变更优先向后兼容。新增字段考虑旧调用方/消费者，删除、重命名、类型变化或语义变化先评估影响，与我确认版本化和迁移方案；必要时让新旧版本并行一段时间。
- 不把 HTTP DTO、Proto message 或消息 schema 直接当作领域模型；在适配器边界完成映射与校验。契约检查和关键提供方/消费方测试应进入 CI。
